# Security Policy

Tenon runs model-driven code on the user's machine and, in later phases, in multi-tenant cloud sandboxes. Security reports are taken seriously.

## Reporting a vulnerability

Do not open a public issue. Email the maintainer (see the GitHub profile of the repository owner) with:

- a description of the issue and its impact
- steps to reproduce or a proof of concept
- the affected version or commit

You will get an acknowledgement within 72 hours. Please allow a reasonable time for a fix before public disclosure.

## Scope

In scope: the desktop app, `packages/kernel`, `packages/contracts`, the permission engine, sandbox integration, MCP host, MCP App rendering, plugin installation.

Out of scope: third-party MCP servers and plugins you install; the model providers' services.

## Design principles

- Every privileged capability lives in the main process; the renderer has no Node access.
- Every subprocess goes through the sandbox wrapper. Restricted commands have no network access by default. MCP stdio servers are an isolation exception: they run with your permissions, guarded by approval when added and a hash of their launch configuration.
- MCP tool annotations and results are untrusted input and never weaken a permission check.
- Permission decisions are auditable: policy and the user may loosen, machines may only tighten.

## Known limitations

These are the current limits of command isolation, based on the [sandbox specification](docs/architecture/04-sandbox/spec.md#已知限制) and its recorded probes. File tools and the agent loop run on the host; only commands enter the OS sandbox. The command allowlist does not govern WebFetch or MCP connections.

Where a receipt offers them, its permission buttons mean:

- **“Allow connections to \<hostname> in this task” / 「在这个任务里允许连接 \<主机名>」** lets commands in this task connect and upload to that host from now on. It lasts for this task only and does not add the host to Settings.
- **“Allow writing to this location only: \<path>” / 「允许写入这一个位置 \<路径>」** adds only the displayed location once, when the exact same command and working directory are used again in this task. Unused permission expires at the end of the next reply and is not remembered.
- **“Allow this command to run without restrictions once next time” / 「允许这条命令下次不受限制地运行一次」** does not start a command when clicked. If the exact same command and working directory are requested again in this task, a second approval is required before it runs once with access to every file you can access and any website. Unused permission expires at the end of the next reply and is not remembered. It binds the command text and working directory, not the contents of scripts that command might execute.

The receipt does not offer the last button when any recorded violation is marked protected, or when all recorded violations are diagnostic observations and the command exited successfully. Long-term host permissions belong in Settings → Permissions & network.

### Network access and isolation

- **Allowlisting a site grants a capability, not an operation.** Commands can upload workspace contents to any allowed site using an attacker's own credentials. This applies to broad sites such as `github.com` and model APIs. The proxy checks CONNECT destinations without terminating TLS, so it cannot restrict a connection to a particular token or operation; domain fronting may also bypass filtering. Tenon never automatically adds provider APIs, user gateways, MCP endpoints or telemetry hosts to the command allowlist. The package-manager preset has the same limitation: `registry.npmjs.org`, used by npm and pnpm, also accepts publishing, so enabling it permits uploading workspace contents as an npm package with someone else's token. `upload.pypi.org` and cargo's publishing host `crates.io` are not in the preset. Settings explains both site-wide access and npm publishing. A disclosed Cowork attack and its token-filtering mitigation are described in [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude); Tenon does not implement that mitigation.
- An allowlisted hostname can point to a private-network address. With a DNS resolver's fake-IP mode, the address check sees only the synthetic address (the probe used `198.18.0.0/15`), not the actual destination.
- There is **no hypervisor isolation**. Commands use macOS Seatbelt or Linux bubblewrap and share your machine's kernel; vulnerabilities in that kernel or sandbox mechanism remain outside this boundary. Cowork's local sessions execute code in a dedicated Linux VM, as described in its [architecture overview](https://support.claude.com/en/articles/14479288-claude-cowork-architecture-overview). Tenon deliberately uses the local toolchain without a VM or image.
- MCP stdio servers run with your permissions, relying on approval when added and the launch-configuration hash. They do not receive command isolation. Windows has no OS command isolation; each command requires approval.
- Upstream proxies are disabled for restricted commands. A machine that can reach the internet only through a corporate proxy cannot connect this way. Tools that ignore proxy variables, such as plain SSH and many database drivers, also cannot connect. Where offered, use **“Allow this command to run without restrictions once next time”** only with its scope above in mind. A JVM stripped of `java.instrument` by jlink cannot start in the sandbox.
- Local and private-network allowlist entries work only for clients using the proxy. The runtime's `NO_PROXY` makes many tools connect directly, which is denied. On macOS, tests that bind local ports fail. Unix sockets are denied, so ssh-agent, gpg-agent and Docker CLI socket access do not work; denied Unix-socket connections leave no violation on either platform and therefore no receipt.
- In Linux's `no-seccomp` degraded state, Unix sockets are unrestricted. Extra read denials cover common D-Bus, Docker, X11 and ssh-agent socket locations, but not other sockets. The file observer is also absent; only proxy network denials are reported.

### macOS privacy and tool compatibility

- The runtime unconditionally allows the keychain services `com.apple.securityd.xpc` and `com.apple.SecurityServer`. A command can trigger a system authorization dialog for Tenon's own `com.yiongspace.tenon` keychain items. Development builds are unsigned, and the dialog does not identify the requester clearly.
- **TCC privacy permissions can extend to commands.** For Tenon launched through Dock, Finder or `open`, macOS treats Tenon as the responsible application. Access to Desktop, Documents, Downloads and similar locations depends on permissions granted to that application, since the sandbox otherwise permits reads except at explicitly denied locations. A command touching a location without permission can trigger a dialog naming Tenon (Electron in development builds). Deny unexpected dialogs during command execution. Tenon's own file tools can legitimately trigger the same dialog when you chose a folder there.

  The denial case was tested on macOS 26.3 on 2026-10-22: a development build launched through LaunchServices, with working directory `/` and no Desktop permission, ran `ls ~/Desktop`. macOS displayed `“Electron” would like to access files in your Desktop folder.` and paused the command. Choosing **Don't Allow** produced `Operation not permitted` and exit code 1. This is a TCC denial, not a Seatbelt denial: the runtime records no violation and the receipt does not show it. The agent incorrectly attributed it to the sandbox in that test.

  For launches from a terminal or IDE, macOS attributes responsibility to the launching program; the VS Code launch in the probe displayed no dialog and `ls` succeeded. The Allow case has **not** been tested. The expectation that allowing access grants it to Tenon and later commands remains an inference, as does access to Mail and Messages after granting Full Disk Access. Do not grant Tenon Full Disk Access. Separating commands' TCC identity from Tenon's requires the later signed helper.
- Clients using the macOS system trust store can fail TLS verification (`OSStatus -26276`). Homebrew pip and Go failed in probes; the sandbox documentation also identifies gh, gcloud and Terraform. The required `com.apple.trustd.agent` service is deliberately not allowed. Where offered, **“Allow this command to run without restrictions once next time”** can avoid this restriction; Python packages can use uv instead. Node, curl, uv and cargo were unaffected.
- Tools that ignore `TMPDIR` and write directly to the per-user temporary directory (`/var/folders/…/T`) cannot create temporary files there. Plain `mktemp` is an example; `mktemp "$TMPDIR/x.XXXXXX"` works.

### Files, links and repository operations

- Already-open file descriptors are not constrained by the sandbox, so spawning passes only the three standard streams. `/tmp/claude` is shared by all sandbox commands and other local users of the runtime, including Claude Code. Even the read-only profile can write there and to `~/.npm/_logs` and `~/.claude/debug`.
- Hard links already pointing outside the workspace before execution remain a limitation. Named protections cover each workspace root; macOS also uses globs for matching names in subdirectories, while Linux does not protect those subdirectory names. The runtime's own scan starts from Tenon's working directory, not the workspace.
- On Linux, runtime 0.0.79 cannot protect the symlink nodes traversed while resolving a denied path, including links inside the target path. A command can delete or replace such a link and write a regular file at its old name. Tenon compares the links after execution and reports a protected violation, which is a warning after the change, not prevention. The macOS probes confirmed that deleting or replacing these links is blocked. If a denied entry is a dangling symlink, its target and missing parent directories cannot be created inside the sandbox on either platform; create those directories outside it.
- On Linux, missing protected names appear as empty mount-point files or directories while a command runs. `git status` showed 17 untracked entries in the Ubuntu 24.04 and 26.04 probes, including `.aws`, `.bashrc`, `.envrc` and `.vscode`; file entries appear as `/dev/null` character devices inside the sandbox. `git add -A` and `git add .` fail entirely on them (exit code 128) and stage nothing. `git add \<path>`, `git add -u` and `git commit -a` work. The command's instructions say not to stage these entries, but the macOS-only evaluations do not establish whether the agent follows that instruction. After a normal call the host retains only real changes. SIGKILL can leave the empty files and directories behind; Tenon removes recorded remnants at the next startup only after the recorded call and bubblewrap have stopped, and only if they still match the generated entries. Runtime detection of file remnants fails with bubblewrap older than 0.5.0.
- On Linux, writing inside an existing read-denied directory, such as `~/.ssh`, `~/.kube` or `~/.config/gh`, can look successful. The write goes into a temporary empty tmpfs covering the directory, disappears at command exit and never changes your real files. The observer still reports a protected violation. Force-killing Tenon can also leave an empty, owner-only (`0700`) `claude-empty-*` directory in `/tmp`. Tenon cannot safely identify its owner from that generated name, so it leaves it for system temporary-file cleanup, usually at reboot.
- `.git/config` and `.git/hooks` are protected at workspace roots, so `git remote add` and hook installation fail. On macOS, subdirectory globs also apply, and creating a repository with `git init` at the workspace root or cloning into a subdirectory fails. Both operations succeeded on Linux, which protects only an already-existing root `.git`. A missing `.claude/` at a macOS workspace root cannot be created either; create it outside the sandbox. Commands such as `git commit` and `git reset` still modify your own repository. HTTPS git on macOS cannot save credentials through osxkeychain (`failed to store: -60008`); the command otherwise works, but denied reads of `~/.netrc` produce counted violations. Three consecutive such calls under session approval end the Run as repeatedly blocked.
- Workspace-write commands can change scripts that you later execute outside the sandbox: `package.json` scripts, Makefiles, `.husky/`, `lefthook.yml` and similar files. This also applies when you use **“Allow this command to run without restrictions once next time”**: approval binds the command and working directory, not the current script contents.

### Credentials, environment and package managers

- Denied credential files prevent file-based login for gh, npm publishing, Docker push and similar tools. On macOS even `gh --version` fails because reading `~/.config/gh/config.yml` is denied; narrowing the denial to `hosts.yml` did not fix it. With default credential locations, kubectl cannot connect to clusters, 1Password CLI cannot obtain a session, Vault and psql lose passwordless login, and Hugging Face cannot download models requiring login. An existing `~/.cache/huggingface/token` also makes otherwise unauthenticated commands such as `hf env` fail (`PermissionError`, exit 1); `stored_tokens` alone does not. Hugging Face 0.34.4 uses `HF_TOKEN` first and avoids reading that file when the variable is present. `kubectl version --client`, `op --version`, `vault version` and `psql --version` worked on both tested platforms. Where a receipt offers it, **“Allow this command to run without restrictions once next time”** also removes these credential-file restrictions.
- Credential denials cover default file locations. Alternate locations selected by `HF_HOME`, `KUBECONFIG`, `PGPASSFILE`, legacy `~/.op` and similar settings are not covered. Tokens already in the command environment are passed through, including `GH_TOKEN`, `HF_TOKEN`, `VAULT_TOKEN`, `PGPASSWORD`, `OP_SERVICE_ACCOUNT_TOKEN` and `OP_SESSION_*`. Any command can read them and upload them to an allowed site. Environment filtering for automatically approved commands belongs to a later phase.
- The main process's `JAVA_TOOL_OPTIONS` is used as the runtime's base value for commands, overriding the same key in the requested command environment. It comes from the environment that launched Tenon. Tenon leaves it intact because deleting it would also affect other subprocesses, including MCP connectors.
- With the package-manager preset enabled, Tenon's package caches are shared across sessions and folders. Poisoned caches, `_npx` packages or cargo registry sources (including `build.rs`) can be executed by later sandboxed npm, npx, pnpm, uv or cargo commands with those later commands' own workspace permissions and allowlist. Your own caches and tools outside the sandbox are unaffected.
- Sandboxed npm and pnpm cannot read `~/.npmrc`, so mirrors, proxies, private scopes and tokens configured there do not apply; they normally use `registry.npmjs.org`. In the probes, npm logged the denied read and continued. The 2026-10-16 pnpm retest still produced a non-diagnostic `~/.npmrc` violation and receipt on every macOS install. If a project's `packageManager` selects another pnpm version, installing it into `~/Library/pnpm` on macOS or `~/.local/share/pnpm` on Linux is denied. pnpm 12 failed on both platforms; Linux also reported a store operation lock and a read-only `~/.local/share/pnpm/global/v11`. pnpm remains in the preset with these limits. Where offered, **“Allow this command to run without restrictions once next time”** avoids them. A workspace `.npmrc` can still override `registry=`; adding that mirror's host to the allowlist may help, but the probe's mirror returned 403, so successful installation by this route is unverified.

### Receipts and background processes

- Linux has no **“Allow writing to this location only: \<path>”** button: file violations come only from a diagnostic observer. Denied reads and direct connections that bypass the proxy leave no violations and have no receipt. Observer paths and proxy usernames are controlled by sandboxed processes, so violations can be attributed to another call; this cannot grant permission. Observed writes are classified using the host's filesystem state when the event arrives. Directory replacement, alternative path spellings or intervening changes can cause an outside write to be mistaken for a workspace write and omitted. This loses the receipt and repeated-denial count, not enforcement. Each wrap resolves at most 4,096 directories with at most 65,536 `lstat`/`readlink` calls; large installs can exhaust that budget, after which workspace writes remain as diagnostics rather than being filtered out (at most 200 recorded violations per call, not counted toward repeated blocking).
- Violations arriving after the settlement window go only to logs. On macOS the runtime checks only the first denial in each log output block; if it is noise or ignored, real denials later in the block are lost too. Tenon sets `OS_ACTIVITY_MODE=disable` for restricted macOS commands to suppress the common diagnosticd case (61 misses in 300 attempts before the change; 60/60 recorded afterward). It does not fix direct-connect denials preceded by curl's configd line (5 misses in 50 attempts), or a second real denial in the same block (inferred from runtime code, not measured). Commands deleting that variable and subprocesses clearing their environment can still lose the diagnosticd case. A denied-operation line containing `mDNSResponder` (always filtered by the runtime), `mach-lookup com.apple.SystemConfiguration.configd` or `mach-lookup com.apple.SystemConfiguration.DNSConfiguration` (Tenon's `ignoreViolations` entries) is also dropped by substring matching. A command can deliberately choose such a path name. The denial still applies, but no receipt or repeated-denial count results.
- Some macOS background processes survive normal completion or Stop. A process can remove `TENON_SANDBOX_MARK` before detaching. Apple platform binaries such as perl, ruby, sleep, bash and zsh can detach via scripted `setsid`, bash `set -m` or double-forking; macOS prevents reading their environment, hiding the marker. They survive normal command completion. Stop can kill directly detached descendants, but not those that first break the parent chain by double-forking. A detached perl was still running five seconds after completion in the probe. With SIP disabled, including on the GitHub macOS runner, the environment is readable and these processes can be collected; CI skips the test documenting the SIP-enabled limitation. Homebrew Python, the command-line tools' Python and git, and fnm Node expose the marker and can be collected. Surviving processes live until they exit, are manually killed or the computer restarts. Their original sandbox read/write rules, including workspace write access, remain even after Tenon exits. While Tenon is running they can use its proxy and receive later sessions' domain grants and user allowlists; quitting Tenon cuts off proxy network access, whose credentials last only for that app launch.

### Snapshots, restore and Delete

These come from the [file bridge specification](docs/architecture/05-file-bridge/spec.md#已知限制与代价). Snapshots, restore and the Delete tool run in the main process with your permissions, outside the command sandbox.

- Command changes enter a snapshot only when the whole folder can be snapshotted. Excluded files, your own `.git` (which `git commit` and `git reset` in a command change), anything sent over the network and anything connectors do cannot be restored. Once snapshots are cleaned up, deleted files cannot be recovered.
- Files ignored only by your global gitignore (commonly `.env`) are copied into snapshots and kept until cleanup.
- The shadow repository's git runs with your permissions outside the sandbox. Only Tenon builds its arguments; it does not read your global git configuration and runs no hooks. A parsing vulnerability in git itself would still act with your permissions.
- A git snapshot cannot tell your changes to the same folder while a command runs from the command's own changes. They count as the command's and are undone on restore without asking. Only changes made after the command ends, such as while an approval is pending, are protected.
- A git directory outside `.git/` that a `.git` pointer file refers to is not on the list of automatically executed locations.
- A link on a protected path created between two refreshes is recognized for direct writes to its final target only after the next refresh. Background processes that escape the process group and connectors' long-running processes are not covered by the restore lease, so during a restore they can change the same files without waiting.
- The scan for link targets skips default-excluded directories such as `node_modules` and does not follow directory links. When a workspace is too large to scan completely, that session recognizes protected paths only by name and real path; changes reaching an automatically executed location through a link are not asked about separately until the next refresh.
- The identity compared before restore acts does not include the inode: a different file with the same size, nanosecond modification time, mode and link count is not detected. If a restore crashes midway, its temporary files remain next to their targets in the workspace.
- Not covered: a link swapped between the decision and the write; something else renaming a name to a different case or Unicode normalization form (the content is restored under that other spelling); hard links on the command side that existed before it ran. The write guard compares only size and nanosecond modification time, so different files matching both are not told apart, which is more likely on file systems with coarse timestamps. Files with more than one name are not restored.
- When a parent directory's spelling changes, restore skips the other spellings together by NFC normalization plus simple lowercasing. Other spellings APFS treats as the same name, such as final ς and σ or the ligature ﬁ and fi, are not included. If the old file cannot be read, the preview may list the file for deletion; the identity check stops that when restore acts and records a failure, so nothing is deleted.
- When a stopped or timed-out command left no after-call snapshot, and a file that existed before it is later changed by the agent, every file the agent created or changed from that command up to that call is also asked about as a conflict, even if nobody else changed anything.
- Read and search do not ask about automatically executed locations or files with more than one name: reading a pre-existing hard link in the workspace that points outside it shows no approval card.
- A restored file's modification time is the moment of the restore, not its time before the task, so it sorts first by modification time.
- Behavior on macOS without the command-line tools, with git older than 2.43, and on Windows has not been tested. On Windows only single-file copies are kept, and the final path component is not protected against link swaps.
