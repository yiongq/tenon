# 规格驱动开发（SDD）

> 下面两个标记之间的内容由 sdd skill 管理，升级时会被整块换掉，不要手改。本项目自己的规则写在后面的「本项目补充」。

## 术语

- **owner**：本项目的主人。**agent**：在本项目里干活的 Claude，包括主会话和它派出的子 agent。
- **spec**：规格说明，写做什么、怎样算做完。**plan**：这份 spec 唯一的进度表。**log.md**：只往后追加的实施、评审、验收记录。
- **核心块**：AGENTS.md 里 `sdd:core` 标记之间的 8 条短规则。本文是每一条的细则。
- **总参考**：`docs/architecture/master-reference.md`，开了路线图才有：一张阶段表，加「目标和不做」「以后再说」两节。**overview**：`docs/architecture/overview.md`，现行的架构总览，只写现在是什么样。
- **门禁**：必须通过的检查，比如格式检查、lint、类型检查、测试。**PR**：GitHub 上的合并请求。**CI**：每个 PR 自动跑的检查。**钩子**：在某个时机自动跑的命令，比如 git 提交时跑的 lefthook，或 Claude Code 每次停下时跑的 Stop 钩子。
- **spec-check**：本项目的检查脚本 `.sdd/spec-check.py`，只用 Python 标准库。规则有没有守住，由它在提交时和 CI 里判，不靠 agent 自觉。每个检查查什么、怎么判、config 里能设什么，见 skill 的 `references/spec-check.md`。
- **验收的三个标记**，写在某条验收后面。**（人工）**：只能靠人看的。**（live）**：要用真 key、真花钱、手动跑的。**（平台）**：只能在某些平台上跑的，写成（平台：macOS）这样。
- **上下文**：一个会话里模型能看到的全部内容。**新上下文**：不继承作者对话的新会话或新子 agent。
- **sdd skill**：装在本机的 sdd 技能（比如 `~/.claude/skills/sdd`）。本文说「见 skill」，就是指它里面的文件。
- **没装 skill 时**（换了只读 AGENTS.md 的其他 agent，或在云端、别的机器上）：规则本身都在项目里，即 AGENTS.md 的核心块、本文和 `.sdd/spec-check.py`，照着做就行。缺的是 skill 里的模板和提示。评审的提示按细则 8 的要点自己写；其余文件按下文「spec 的节」「plan.md」的格式手写。不要凭印象复述 skill 里的原文，需要时在 plan 的「需要你」里请 owner 装 skill 或把文件贴过来。
- 「standard 起」指 standard 和 heavy 两档都要。

## 档位和模块

本项目有三个档位。一个档位就是一组模块，加一组体量上限，再加 spec-check 里哪些检查会拦。

- lite：只有核心块。
- standard：核心块 + 路线图（roadmap）+ 架构与参考（architecture）+ 入口页（index）+ 决策卡（decisions）。
- heavy：standard + 先核实（evidence）+ 挑刺评审（critique）+ 验收矩阵（matrix）。
- 逐条替换（replace）和私有笔记（notes）哪档都不默认开，要用时在 `.sdd/config.json` 的 `modules` 里单独开。
- 项目默认档写在 AGENTS.md 核心块标记的 `tier=` 里。每份 spec 的页头有自己的 `Tier:`，可以比项目默认档高，也可以低。选档、升档降档怎么做，见 skill 的 `references/modes/spec.md` 和 `references/modes/upgrade.md`。
- 本文只收了项目默认档要用的模块的规则。某个模块的规则不在本文里时（没开，或者这份 spec 的 `Tier:` 比项目默认档高），读 skill 的 `references/modules/<id>.md` 照做。模块 id 是 roadmap、architecture、index、decisions、evidence、critique、matrix、replace、notes。

**体量上限**是起步值，超了只报警。

| | lite | standard | heavy |
|---|---|---|---|
| spec 全文 | 不超过 3 千字符 | 不超过 1.5 万 | 不超过 2.5 万；超了按子阶段拆，比如 4a、4b |
| 给你看的一页 | 不单设，整份 spec 都用平常话写 | spec 第一节，不超过 40 行 | 同左 |
| plan.md | 不超过 3 千字符 | 不超过 1 万 | 不超过 3 万 |
| AGENTS.md | 不超过 40 行（含核心块） | 不超过 200 行，且不超过 24 KiB | 同左 |

## 状态和改法

```
draft ──owner 批──► ready ──owner 验收──► implemented（正文冻结）
直接改原文          收紧、澄清：直接改，记一行修订     要改就写新 spec：
                    放宽、改已合入接口：先要 owner     ├ 只加一节内容：Changes（增补）
                    点名批准                           ├ 换掉一节：Changes（替换），要开逐条替换
                                                       └ 整份换掉：Changes（取代），旧的标 superseded
```

## 核心块 8 条的细则

### 1. 两个文件
- 每个目标一个文件夹，放在 `docs/features/<目标>/`。开了路线图时，阶段性的 spec 放在 `docs/architecture/NN-<目标>/`，NN 是两位数编号。spec 的 id：architecture 下是两位编号，features 下是目录名。
- `spec.md` 写做什么、怎样算做完；`plan.md` 是唯一的进度表；有记录时才建 `log.md`，只往后追加。按档位和模块，还可能有 `decisions.md`（决策卡）和 `evidence.md`（先核实）。不建 tasks.md、TODO.md。
- 写新 spec 前，先读项目的「目标和不做」：开了路线图时是总参考里的「## 目标和不做」，lite 项目是 AGENTS.md 项目介绍后面的「不做：…」那一行。新 spec 要做的事碰到了「永远不做」的条目，或新 spec 的「不做」和它对不上，出一张决策卡让 owner 定，不自己取舍。改这一节要有 owner 的原话。

### 2. 开工与交接
- owner 说「继续」「开工」，或者没有指令时，agent 找 `Status: ready`、plan 里还有没勾步骤的 spec。只有一份就接着做；多于一份就问 owner。开了路线图时，先挑 architecture 下编号最小的；没有，再看 features。
- 动手前说清挑了哪份、哪一步。`python3 .sdd/spec-check.py --status` 会打印开工规则选中了哪份、哪一步，还会列出「要你做的」：所有「需要你」不为空的 spec、挡上线的「以后再说」、还没回的「交 owner」。
- 停下前重写 plan 的「当前 / 需要你」和「交接」。「需要你」写清现在要 owner 做什么；「交接」写清下一个会话从哪里接。
- plan 只剩最后一步「owner 验收 → 改 Status」没勾时，停下等 owner，不自己改 Status，也不去选下一份 spec。
- 验收时，agent 带 owner 在真应用上走一遍「怎么算做完」和所有（人工）条目，顺带核对 README 里的启动命令还能跑；`--status` 同时列出这份 spec 放宽过的测试和理由。人工验收的截图放 `<spec 文件夹>/walkthrough/`，文件名带验收号，log.md 按文件名引用；公开仓库里只放用假数据拍的。

### 3. 状态与批准
- draft 是草稿，ready 是批准开工，implemented 是已完成，superseded 是被新 spec 整份取代。
- 改成 ready、implemented 只由 owner 定。请 owner 回一句带编号的话，比如「05 改 ready」；agent 在页头加一行 `Approved:`，格式见下文「页头」。例子：`Approved: ready · 2026-10-20 · 「01 按推荐，改 ready」· 对话`。
- 不算批准的原话：去掉标点和空白后，等于「继续」「开工」「好」「好的」「可以」「行」「ok」「都按推荐」「按推荐」「全部按推荐」之一；或者没点名这份 spec。点名的意思是，原话里有它的两位编号、目录名、标题正文，或标题括号里的别名。spec-check 的 `approval` 检查会拦这两种；它验证不了 owner 是不是真说过，只保证有原话可查。
- implemented 之后不往回退，要改走第 4 条。ready 退回 draft，只在 owner 说的时候，并记一行修订。
- 决定不做一份还没 implemented 的 spec：先退回 draft，再删掉它的文件夹，提交说明写理由；总参考里有这一行的，状态列写「不做 · 理由」。只是先搁置：退回 draft，在 plan 的「需要你」里写明在等什么。
- 整批采纳推荐项：写明范围才算数，比如「05 D1–D12 按推荐」。选错难退的卡，每张另写一行，比如「D7=A」。

### 4. 改动两条路
- implemented 之前直接改原文。从 ready 起，每次改动在「修订记录」记一行：日期 · 哪一节 · 为什么 · 相关的提交号或 PR 号。同一个提交写不进自己的提交号，所以写已有的相关提交或 `PR #n`；脚本不查这一栏。不照抄旧文，旧文 git 里有。
- 实现中只收紧或澄清的修订，可以直接改，和代码放在同一个 PR 里。放宽要求，或者改已合入的接口，先要 owner 点名批准。
- implemented 之后正文不动。要改就新写一份 spec，用页头连起来：
  - 只加不减：新 spec 页头写 `Changes: 00 §落盘格式（增补）`，正文写一节 `## 对 00 的增补`，写全文。
  - 换掉某一节：`Changes: 00 §落盘格式（替换）`。项目要先开逐条替换模块，规则在 skill 的 `references/modules/replace.md`。
  - 整份取代：新 spec 写 `Changes: 00（取代）`，旧 spec 标 `Status: superseded by 05`。
- 旧 spec 那边只在页头加一行 `Changed by: 05（§落盘格式）`，正文一个字不动，行末也不加指针。

### 5. 写法
- 引用文档写节名，引用代码写「路径 + 函数名或类型名」，不写行号。
- 代号指 D3 这类短编号。代号必须在本仓库有定义，正文先写规则本身，代号只放句末当出处。仓库外的编号也只当出处，实现的人不去查它也能照着做。
- 术语第一次出现时解释（项目有 overview 的「术语」表时，写「见 overview §术语」也算）；一段一件事；决策历史放 decisions.md 或附录，不放正文。新增的行不超过 600 个字符，超了 spec-check 的 `shape` 检查会报警。

### 6. plan 只放进度
- plan 只放：步骤、「当前 / 需要你」、最新一条交接、Open。最后一步是「owner 验收 → 改 Status」。不列「开 PR」「合并 PR」这类步骤。实施、验收、评审记录写进 log.md。
- Open 是还没定的问题，每条写清什么时候、凭什么能定。子步骤编成 10.1 这样，不重新排号。「当前 / 需要你」每次整块重写。
- owner 给的指令如果改变了 agent 做事的方式，写进 AGENTS.md 核心块外面，不要只留在某一份 plan 里。
- AGENTS.md 的「硬规矩」每条行末写「（由 <门禁或脚本> 守）」或「（没自动化，靠评审）」。删改或放宽「硬规矩」和本项目补充里的规则，要 owner 点名批准，提交说明写 `规则改动：哪条 · 为什么 · 「原话」`；spec-check 会把这两处被删改的行列给评审（只报警）。
- 实施中发现、下个会话还要用的事实，不要只写在 log、交接或 agent 自己的记忆里。版本约束写进 overview 技术栈表的「为什么选」列（没有 overview 的项目写进 AGENTS.md）；操作须知（环境和工具的坑）写成 AGENTS.md「开发」一节里的一条短条，AGENTS.md 快到 200 行时，拆到 `docs/architecture/dev-notes.md`，原处留一行链接。
- 只管一份 spec、有期限的授权，写成那份 plan「当前」里的一行：`授权：范围 · 到什么时候 · 「原话」`。
- 把 spec 改成 implemented 的那个 PR 里，这份 spec 没解决的开放问题、plan 的 Open 和跟进事项，要么挪进总参考的「## 以后再说」（lite 项目用 `docs/later.md`），要么写明已经定了。这件事要在派评审之前做：评审之后，spec 正文就不能再改了，只能改页头的 Status 和 Approved。「以后再说」每条一行，写成 `什么事 · 谁做 · 什么时候做或挡着什么 · 出处`。它不是工作队列，开工规则不从这里挑活；要做哪一条，先写 spec，写了就把那一行换成链接。

### 7. 做完前过检查
- 每条验收都要有测试点名它，或者标（人工）/（live）。这两种验收进 owner 的验收清单。（平台）的验收照样要有点名它的测试；那条测试在别的平台的 CI 上被跳过时，只报警不拦，这条验收也进 owner 的验收清单，由 owner 或在那个平台上的会话确认。
- standard 起，测试用例名带「spec 编号或名字 + 验收号」，比如 `04 验收 7: …`；一条用例点名多条时写 `04 验收 7、8`。spec-check 的 `trace` 检查（查验收和用例一一对应）靠它对号。
- 修 bug 先写一个能复现它的失败测试，用例名带「复现」，再修。
- 改弱已有测试（删断言、加跳过、放宽阈值、改期望值），写一行 `测试改动：文件 · 用例 · 为什么`。standard 起写进 log.md；lite 写进 log.md 或提交说明都行。spec-check 的 `tamper` 检查（标出被削弱的测试）按这一行放行。
- 说做完之前，跑项目的检查（至少测试）和 `python3 .sdd/spec-check.py`。在 agent 环境里跑不了的测试（接入时用 `--measure` 实测过），说做完前以 CI 结果为准；没有 CI 的项目，列进 owner 的验收清单。
- lite 不强制装钩子，说做完之前由 agent 自己跑上面这些；脚本不查测试底线，靠新会话里那次评审，对一遍验收和测试的对应。
- standard 起，测试由 CI 强制，不过不能合并。提交时的钩子跑哪些检查，按接入时的实测定，写在 `.sdd/config.json` 里；变慢了，`timing`（盯提交耗时的检查）会提醒重测。
- 派实现子 agent 时，提示里固定带上「实现三句」：测试有错就直说；不为某个用例写死结果；同一处反复跑红就停下报告。
- 测试怎么分层、怎么先写测试、怎么防作弊，见 skill 的 `references/testing.md`。

### 8. 独立评审
- 说做完或合并之前，在新上下文里评审一遍，带证据的问题修掉。证据是一条会失败的测试、一处故意改坏而测试没发现的代码，或者能照着做的复现步骤；没有证据的只算建议。评审只出发现，不改代码。
- standard 起另有两条：评审记录写进 log.md 并绑定审过的提交号；只有评审能打开自动合并（auto-merge：检查全过后由 GitHub 自动合并），作者不开。
- 三种情形评审通过也不开自动合并，等 owner 来合：改了门禁文件（`.github/workflows/**`、lefthook.yml、`.sdd/config.json`、`.sdd/spec-check.py`、`.claude/settings.json`、测试运行配置）；碰了 AGENTS.md「Git」一节写明「合并就会发布或部署」的路径和分支；带证据的 blocker（不修不能合的问题）的处置写了「交 owner」。
- 评审包怎么出、提示模板、记录格式、停止规则、各档做到哪一步，见 skill 的 `references/review.md`。

## spec-check 按这些格式读

### 页头
- 页头是 H1 到第一个 `## ` 之间的部分。每个键占一行，写成 `键: 值`。
- 「新写的 spec」：本次检查范围内新增的 spec.md，或在 `.sdd/config.json` 的 `baseline_commit`（接入已有项目时记下的起点提交）之后新增的 spec.md。格式类检查只查新增的行，旧文档里的老写法不追究。
- `Status:` 取 `draft`、`ready`、`implemented` 或 `superseded by <ref>`。`Tier: <lite|standard|heavy> — <一句理由>`，新写的 spec 必须有。`Phase: N`，开了路线图的阶段性 spec 写。
- `Changes: <ref> §<节>（增补|替换[：说明]）`，多条用「；」隔开；整份取代写 `Changes: <ref>（取代）`。`Changed by: <ref>（§<节>）`，多条用「；」隔开。
- `Approved: <状态> · YYYY-MM-DD · 「逐字原话」 · <对话|PR #n|路径>`，每次批准一行，owner 批准后由 agent 加。
- `<ref>` 可以是两位编号、目录名，或指向那份 spec.md 的 markdown 链接。`§节名` 匹配那份 spec 里任一级标题：全等，或者标题以节名开头、后面紧跟空格或括号，全角、半角括号都认。
- 项目里已有别的页头写法（比如 `Supersedes in part`）时，在 `.sdd/config.json` 的 `header_aliases` 里登记。

### spec 的节
standard、heavy 的 spec 按这个顺序排；lite 的 spec 没有第 1 节，整份用平常话写。
1. `## 给你看的一页`：给 owner 批 ready 时读，不超过 40 行，不放代号（「要你定的」那一行除外）。有单独一行 `做什么：…`（入口页会读它），「怎么算做完」每条标 `（验收 N）`。
2. `## 外部依据`（用到的外部事实和一手来源，用不到写「无外部依赖，未调研」）、`## 接口`（真实签名，只写新增和改动的部分）、`## 一直要成立的规矩`（每条一句，写得能直接变成测试里的一条检查）。
3. `## 验收标准`、`## 开放问题`、`## 修订记录`。

### 验收和「实现位置」
- 验收是 `## 验收标准` 下的顶层列表项，写成 `N.` 或 `N、`，不支持 7a 这类子编号。写看得见的结果，不写实现。只能人看的标（人工），要真 key 的标（live），只能在某些平台上跑的标（平台：macOS）这样，全角、半角括号都认。
- 「怎么算做完」里统一写 `（验收 N）`，spec-check 会查这些号存不存在。想让入口页列出代码位置，在对应的节里写单独一行 `实现位置：<路径> → <名字>`。

### plan.md
```
# <spec 编号或名字> · plan
## 当前 / 需要你
当前：……
需要你：……（没有就写「无」）
## 步骤
- [x] 1. ……
- [ ] 2. ……
  - [ ] 2.1 ……
- [ ] N. owner 验收 → 改 Status
## 交接
（只留最新一条）
## Open
```
- 最后一步的字面固定是「owner 验收 → 改 Status」。只剩它没勾，spec-check 就判定「在等 owner 验收」。
- 规定以外的 `## ` 标题由 `shape` 报警。项目要多一节，登记在 `.sdd/config.json` 的 `plan_extra_headings`。

### log.md、decisions.md、evidence.md
- log.md 的条目头：`## 实施 · 日期`、`## 验收 · 日期`、`## 评审 · 日期 · 审过 <提交号>`。单行条目：`测试改动：文件 · 用例 · 为什么`；真花钱的调用写 `花费：日期 · 做了什么 · 实花 · 累计 / 上限`，上限写进 spec 的「代价和已知限制」；碰了线上环境的操作写 `线上操作：日期 · 做了什么 · 「原话」`。
- decisions.md：每张卡一个 `### D1 · 问题`；末尾 `## owner 原话`。项目级的拍板记在 `docs/decisions.md`，卡号用 R1、R2……
- evidence.md：事实写 `### E1 · …`，附一手来源；探针写 `### P1 · …`，附「结果是 X 就改什么」和实际结果。
- 代号前缀默认有五个：D 是 spec 里的决策卡；E 是 evidence.md 里一条核实过的事实；P 是 evidence.md 里的一个探针；M 是 log.md 里评审登记的一个突变；R 是项目级拍板（`docs/decisions.md`）。项目可在 config 的 `code_prefixes` 里加别的前缀。

## 模块：路线图（roadmap）

这个模块管整个项目，跟着项目默认档。standard、heavy 默认开。

- 总参考：`docs/architecture/master-reference.md`，整份不超过约 80 行。它由三块组成：一张阶段表，一节「## 目标和不做」，一节「## 以后再说」。
- 阶段表每个阶段一行，列为「阶段｜目录｜一句话｜状态｜关键决策」。
- 阶段性的 spec 放在 `docs/architecture/NN-<目标>/`。NN 是两位数编号，编号不重复，spec-check 的 `numbering` 检查会拦重复的编号。
- 开工时按编号挑：没有指令时，agent 先挑 architecture 下编号最小、`Status: ready`、plan 里还有没勾步骤的那份；没有，再看 features。
- 阶段性的 spec，页头写 `Phase: N`。

**怎么维护阶段表**

- 新开一个阶段，先在总参考里加一行，再建目录。编号取现有最大编号加 1。
- 「状态」列跟着那份 spec 的 `Status:`，spec 的状态变了，同一个 PR 里改这一格。
- 「关键决策」列只写一句话，需要出处时写决策卡的代号，比如 D3。决策历史放 decisions.md，不堆进总参考。
- 路线里写了、目录还没建，是正常的。目录有了、总参考里没有，要补上。
- 总参考每个阶段只占一行，不写实施过程。
- 决定不做的阶段：它的 spec 按核心细则第 3 条先退回 draft 再删掉，总参考里那一行的状态列写「不做 · 理由」，不删这一行。

**「目标和不做」一节**

- 写三件事：给谁用，解决什么问题，永远不做什么。不超过 15 行。init 或 adopt 时顺带向 owner 问出来。
- 写新 spec 之前先读它。新 spec 要做的事碰到了「永远不做」的条目，或者新 spec 的「不做」和它对不上，不要自己取舍，出一张决策卡让 owner 定。
- 改这一节要有 owner 的原话，原话记进 `docs/decisions.md`。
- lite 项目没有总参考，在 AGENTS.md 那句项目介绍后面加一行「不做：…」。

**「以后再说」一节**

- 放说好以后回来做的事：延后的范围、技术债、没修的 bug、评审里「不修」的 major。每条一行：`什么事 · 谁做 · 什么时候做或挡着什么 · 出处`。
- 第三栏写「挡上线」的条目，`--status` 会单独列出来，别的条目只报条数。
- 把 spec 改成 implemented 的那个 PR 里，那份 spec 没解决的开放问题、plan 的 Open 和跟进事项，要么挪进这一节，要么写明已经定了。改成 implemented 时 Open 还不是「（无）」，spec-check 会报警。
- 这不是工作队列：开工规则不从这里挑活。要做哪一条，先写 spec；写了，就把这一行换成指向那份 spec 的链接。
- lite 项目没有总参考，用 `docs/later.md`，写法一样，有第一条要记的再建。

```
- 换掉临时的限流写法 · agent · 用户过千之前 · 03 开放问题
- 完成个人信息保护影响评估 · owner · 挡上线 · 05 plan
```

## 模块：架构与参考（architecture）

这个模块管整个项目，跟着项目默认档。standard、heavy 默认开。它放四类长期要用的文档：系统现在是什么样（overview）、我们参考了谁（reference）、我们依赖的厂商现状，以及一直有效、可以原地改的现行文档；要部署到服务器的项目，再加一份运维手册。spec 写的是「这一次要做什么」，做完就冻结；这些文档写的是「现在是什么样」，随时有效。

**overview：现行架构总览**

- 路径 `docs/architecture/overview.md`，不超过 200 行，只写现在是什么样。过去为什么这么定，放 decisions.md 和各份 spec。
- 必有四样：模块和边界；数据流；技术栈表，列为「技术｜版本｜为什么选｜在哪份 spec 或 R 卡定的」；一张 ASCII 图。R 卡是项目级拍板的卡，记在 `docs/decisions.md`。
- 可选三节：
  - 开头的「## 给你看的一页」：大白话，不超过 40 行，给不读代码的人看。
  - 「## 信任边界」：谁可信、检查放在哪一侧，不超过 15 行。本项目补充里写了安全类的升档条件时，必须有这一节。安全角度的评审先读它；新 spec 打破了里面的假设，按 blocker（不修不能合的问题）报。
  - 末尾的「## 术语」小表，一词一行。别的文档里术语第一次出现时，写「见 overview §术语」就算解释过。
- 要部署的项目，加一行「运行在哪」，链到运维手册。
- 实施中发现、下个会话还要用的版本约束，写进技术栈表的「为什么选」那一列，不要只留在 log、交接或 agent 自己的记忆里。

```
| 技术 | 版本 | 为什么选 | 在哪定的 |
|---|---|---|---|
| 某库 | 4.x | 只能用 4.x：5.x 删掉了我们用的接口，升级前要先改适配层 | 02 D3 |
```

**reference：参考产品和项目的笔记**

- 路径 `docs/reference/<产品或项目>.md`，一份一个。写它怎么做、我们抄什么、不抄什么，每条结论附一手来源（官方文档、源码、发布说明），不附转述文章。
- 怎么收费、市场多大、卖给谁这类商业判断不写在这里，放私有笔记。

**厂商现状：我们依赖的外部厂商**

- 我们依赖的外部厂商（模型、云服务、第三方接口）也放在 `docs/reference/` 下，写成一张能力表：一个厂商一份，或者所有厂商合成一份 `vendors.md`。
- 每行写：能力、实测结果、核实日期、一手来源、哪些 spec 依赖它、什么时候重核。
- 为什么单列：evidence.md 跟着单份 spec，写完就不再更新，看不出哪条事实是哪天核实的；这张表是现行的。实测出新结果、厂商文档变了，就改这一行和核实日期。
- 「X 不支持 Y」这类说没有的话，也要实际查过才能写进来；查不实的标「未核实」。
- 已经 implemented 的 spec 引用的事实后来变了，spec 正文不改。产品要跟着变的，另写一份新 spec（核心的改动两条路）；不用变的，能力表上改了就够。

**现行文档：一直有效、可以原地改的文档**

- 比如设计系统 `docs/ux/`、评测协议、API 风格；overview 和 reference 也按这套规矩管。
- 它们的路径列在「本项目补充」里，一类一行，写成 `现行文档：路径 · 管什么`。
- 每次改，在文末的「## 修订」记一行：日期 · 改了什么 · 为什么 · 相关的提交号或 PR 号。
- spec 引用它时写节名，不写行号。两边对不上时以 spec 为准，再把现行文档改过来。
- 文档里由脚本或门禁执行的规则，写明「由 X 守」，比如「组件里不许写死颜色（由 check-colors 守）」。
- 增删或放宽这类规则条目，按「改动碰到了什么」选档，该写 spec 的写 spec。

**运维手册：只有要部署到服务器的项目才建**

- 路径 `docs/ops/runbook.md`，不超过 300 行，超了按操作拆开。
- 按操作分节：首次装机；发版和部署；回滚（含回不去的版本）；备份和恢复；配置和密钥；告警怎么处理。
- 配置和密钥一节只写变量名，和它放在哪个 env 文件。主机名、域名、IP 放私有笔记，不写进公开仓库。
- 手册写了步骤，不等于授权：部署、读写线上库这类操作，照 AGENTS.md 的硬规矩，每次要 owner 在当次会话里点名。
- 监控、告警、值班本身归项目自己的 ops 文档，这里只写告警来了怎么处理。

**什么时候要在同一个 PR 里更新它们**

- 改了模块边界、数据流、技术栈（含大版本升级、换依赖、抬高运行时下限）：更新 overview，技术栈表那一行也一起改。
- 实测出厂商的新事实，或旧事实变了：更新厂商能力表和核实日期。
- 改了部署脚本、迁移或环境变量：更新 runbook 和 `.env.example`（只写变量名，不写值）。
- 改了现行文档：在它的「## 修订」里记一行。
- spec-check 帮着盯，只报警，不拦：overview 超过 200 行、runbook 超过 300 行，会报警；本 PR 改了 spec 的「接口」一节，或动了 `.sdd/config.json` 里登记的模块路径（`architecture_paths`）、运维路径（`ops_paths`），却没动 overview 或 runbook，也会报警，并列给评审。要不要改，由评审判断。

## 模块：入口页（index）

这个模块管整个项目，跟着项目默认档。standard、heavy 默认开。

- 入口页是 `docs/README.md`，整份由脚本生成，首行写「由 spec-check --index 生成，勿手改」。
- 重新生成：`python3 .sdd/spec-check.py --index`。改了 spec 页头、plan 的「需要你」、「实现位置」，就在同一个 PR 里重新生成。
- spec-check 的 `index` 检查在内存里重新生成一份，和 `docs/README.md` 不一样就报「过期」。

**入口页里有什么**

- 上半部分：每份 spec 一行，写 Status、spec 里「做什么：」那一行（没有就用标题）、plan 里的「需要你：」。所以「给你看的一页」里要有「做什么：」这一行，plan 里要有「需要你：」这一行。
- 下半部分「被改过的节」：由各份 spec 的 `Changes:` 页头和「实现位置：」行生成。每一节后面按时间列出改过它的 spec 节和实现位置。

```
01 §Provider 层  ← 02 §对 01 的修补 ← custom-vendors ← model-display-names
   实现位置：packages/kernel/src/provider/types.ts → ModelInfo
```

**怎么查「这一部分现在长什么样」**

- 看入口页的「被改过的节」，顺着链读几小节。spec 仍然是正本，入口页不是第二份真相，它只告诉你该读哪几节、代码在哪。
- 要让入口页列出代码位置，就在 spec 的那一节里写单独一行：`实现位置：<路径> → <名字>`。路径是文件，名字是函数名或类型名，不写行号。

**什么时候会报警**

- `Changes` 指的节名，在旧 spec 里不存在。
- 「实现位置」的文件不存在，或者文件里找不到那个名字。
- 内容和代码是不是真的一致，脚本查不了，靠评审。

## 模块：决策卡（decisions）

这个模块管单份 spec，跟着那份 spec 页头的 `Tier:`。standard、heavy 默认开。

- spec 旁边放 `decisions.md`。每张卡一个 `### D1 · 问题`，末尾一节 `## owner 原话`。
- 代号前缀默认有五个：D 是 spec 里的决策卡；E 是 evidence.md 里一条核实过的事实；P 是 evidence.md 里的一个探针；M 是 log.md 里评审登记的一个突变；R 是项目级拍板（见下文「项目级拍板」）。项目可以在 `.sdd/config.json` 的 `code_prefixes` 里加别的前缀。
- 正文里出现的代号，spec-check 的 `codes` 检查会去 decisions.md、evidence.md、log.md 的标题里找定义，找不到就报警。R 开头的代号，在 `docs/decisions.md` 的标题里找。

**每张卡写什么**

- 编号（比如 D1）和问题。
- 每个选项的代价。
- ★ 推荐项。
- 选错了难不难退。

```
### D3 · 重复的发票怎么判
- A ★ 按发票号 + 金额判重。代价：同一张发票重新扫描后金额识别错一位就会漏判。
- B 按图片内容哈希判重。代价：同一张发票换个角度拍就判不出来。
- 选错难退吗：难退。判重规则决定了归档文件的命名，换规则要迁移已有文件。
```

**规矩**

- 每张卡都给 owner 看，每张都标出 ★ 推荐项。不替 owner 默认，也不挑着问。
- 整批按推荐：owner 写明范围才算数，比如「05 D1–D12 按推荐」。选错难退的卡，每张另写一行，比如「D7=A」。
- owner 的原话逐字记在 decisions.md 末尾的 `## owner 原话`，附上出处（对话、PR 号或文件路径）。
- spec 的「给你看的一页」里，「要你定的」那一行写清有几张卡、是否都标了推荐、有几张选错难退。

**没开这个模块时**（比如 lite 档的 spec）

- 要定的事不超过 2 件：在对话里问，每件标 ★ 和代价，答案直接写进 spec，被否掉的方案不记。
- 要定的事超过 2 件：给这份 spec 建一个 decisions.md，照上面的规矩来。

**项目级拍板：`docs/decisions.md`（standard 起默认有）**

- 不属于任何一份 spec 的决定，记在项目级的 `docs/decisions.md` 里：产品范围、许可证、评测协议、流程规矩这一类。owner 在 spec 之外拍的板，当天记进来。
- 格式同 spec 的决策卡，多一行「什么情况改判」，末尾一节 `## owner 原话`。代号用 R1、R2……
- 代码注释和别的文档里只写「见 docs/decisions.md R3」，不重抄理由。
- 新的一张卡推翻旧卡时，在旧卡的「结果：」后面补一句，比如「被 05 D2 推翻」。这个文件不冻结，所以能这样补。
- 项目里已经有 `docs/adr`（架构决策记录）的，就把它当登记处，不另建 `docs/decisions.md`；代号沿用它自己的编号。

```
### R1 · 用什么许可证
- A ★ Apache-2.0。代价：要保留版权和专利声明，改过的文件要标出来。
- B MIT。代价：没有明写的专利授权。
- C 暂不开源。代价：别人不能合法地使用和改动。
选错难退吗：难退。公开之后，别人已经按旧许可证拿走了代码。
什么情况改判：要接受外部贡献，或者要并入别的许可证的代码。
结果：选 A · 2026-11-03
```

## 模块：逐条替换（replace）

这个模块管整个项目。默认不开，要用时在 `.sdd/config.json` 的 `modules` 里加上 `replace`，并写明能换的范围。

- implemented 的 spec，其中项目规定范围内的某一节，可以被新 spec 单独换掉，不用整份取代。
- 新 spec 页头写 `Changes: 00 §节名（替换）`。要说明的话写成 `（替换：说明）`。
- 旧 spec 页头加一行 `Changed by: 05（§节名）`，正文一个字不动。
- 新 spec 里写一节，给出替换后的全文。入口页的「被改过的节」会把这次替换列出来。

**能换哪些条款**

- 范围写在「本项目补充」里，同时记进 config 的 `modules`。比如「只许替换表现层的条款」，或者「任意条款」。
- 每次要用之前，先判断这一节在不在范围内。不在，就整份取代：新 spec 写 `Changes: 00（取代）`，旧 spec 标 `Status: superseded by 05`。

**检查怎么看**

- 页头写了（替换），但没开这个模块，spec-check 的 `pairs` 检查会拦。
- `Changes` 和 `Changed by` 要成对出现，缺一边也会拦。

## 模块：私有笔记（notes）

这个模块管整个项目。默认不开。仓库会公开、而且有不能公开的内容时，在 `.sdd/config.json` 的 `modules` 里加上 `notes`，并写明笔记路径和敏感词表。

- 笔记仓库是 `../<项目>-notes/`，必须是 git 仓库，必须私有。
- 里面按「日期-spec 名/」分目录，每个目录下可以有 `reviews/`、`probes/`、`research/`。

```
../<项目>-notes/
  2026-11-01-05-file-bridge/     reviews/  probes/  research/
```

**什么放进笔记，什么不放进公开仓库**

- 商业判断（怎么收费、赚多少钱、卖给谁这类）不进公开仓库。公开文档里最多留一句「另记」，不写内容。
- 评审的原文放 `reviews/`，探针的原始输出放 `probes/`，调研的原始材料放 `research/`。公开仓库里的 log.md、evidence.md 只留结论。

**哪些东西不进笔记仓库**

笔记仓库放的是文字：评审、调研、探针的结论和少量原始输出。下面这些不进 git。

- 能重新下载或重新生成的不进：探针下载的工具和安装包、缓存、`node_modules`、Python 的 `venv`、构建产物、能用命令重跑出来的大块运行输出。很多小文件组成的目录（`node_modules`、`venv`）单个文件都不大，也是整个目录不进。笔记里留一行「怎么重新拿到」：命令，或者下载地址加版本。
- 新项目的约定：下载来的工具放进 `.tools/`（带点），缓存放进 `.cache/`。skill 里的模板 `assets/templates/notes/gitignore` 忽略这两种目录名，不忽略普通的 `tools/`，因为私有扫描脚本常放在 `tools/` 下，它必须进 git。
- 单个文件超过 50 MB 的不提交。提交前，在笔记仓库根目录查一遍会提交的文件：`git ls-files -co --exclude-standard -z | xargs -0 sh -c 'find "$@" -maxdepth 0 -size +50M' sh`，没有输出才行。别用 `find . -size +50M`：它连已经被 .gitignore 挡住的文件（`local-only/` 里的原件、`.tools/` 里的工具）也列出来，按上面的布局永远有输出，分不出这次会不会提交大文件。GitHub 拒收 100 MB 以上的单个文件。
- 带 `.git` 的子目录（探针里建的仓库、克隆下来的源码）不要直接放进笔记仓库。没有提交的，`git add` 直接报错；有提交的，只存成一个指针，内容进不了笔记仓库，证据被悄悄漏掉。查法：`find . -name .git -not -path ./.git`。能重跑出来的，目录加进 `.gitignore`。要留作证据的，由 owner 定：去掉里面的 `.git` 当普通文件提交（历史没了，内容进仓库），或者忽略（内容不进仓库）。
- 受限资料（只许在本机读的原件）放在笔记仓库的 `local-only/` 下，.gitignore 挡住，永不提交，也不推任何远端。下面「受限资料」那一行里的「放在哪」，写 `local-only/` 下的路径。拿不回来的原件（比如旧版本下架了），另做一份 git 之外的备份，比如移动硬盘。自己写的结论和报告写在 `local-only/` 外面，链接指进去；别和原件混在同一个目录里，否则结论也跟着被挡住，没有历史。
- 已有的笔记目录：受限资料和下载物不在约定位置的，不挪位置，别处的文档引用了这些路径。把它们的目录逐条加进笔记仓库自己的 `.gitignore`。整块忽略一个受限原件目录之前，先数一数里面被挡住的 `.md`：这类目录里常混着自己写的结论和报告。这些能不能提交，由 owner 定，不替他挡也不替他放行。做法见 `references/modes/adopt.md` 第 2 步。
- 笔记仓库必须是 git，要有历史，能回滚。推不推私有远端由 owner 定。要推，先把要推的总量和最大的几个文件列给 owner 看。

**敏感词扫描**

- 敏感词表按项目配，写在 config 的 `modules` 里。注意：`.sdd/config.json` 会提交进公开仓库，所以词表本身也是公开的，只放公开了也无妨的通用词。本身就保密的词（内部代号、客户名之类），不要写进词表；改用笔记仓库里的私有扫描，在本地跑，扫描脚本和词表都留在笔记仓库里。
- spec-check 的 `notes` 检查：文档里引用的笔记目录不是 git 仓库，就报警；目录不存在就跳过（CI 里本来就没有）；git 跟踪的 .md 文件（含公开仓库里的 `research/`）出现敏感词，也报警。
- 报警后，把那段内容挪进笔记仓库，原处留一句「另记」。

**受限资料**

- 有些资料只许在本机读，不许抄进仓库，比如拆解别人产品得来的私有材料。在「本项目补充」里加一行：`受限资料：放在哪 · 能读什么 · 不许抄什么 · 由哪个扫描守`。
- 「由哪个扫描守」写笔记仓库里的私有扫描。spec-check 的 `notes` 检查只扫 git 跟踪的 .md 文件，守不了别的文件类型，更守不了词表之外的内容。

## 本项目补充

只写这个项目自己的规则；通用规则要改，走下面的「待回流 skill」，不要改上面的受管区。删改或放宽这一节里的规则，要 owner 点名批准，提交说明写 `规则改动：哪条 · 为什么 · 「原话」`。

1. **出处**：这套做法最早参考 DeepChat 的 `docs/spec-driven-dev.md`（Apache-2.0）；2026-10 起换成 sdd v2。架构由 owner 拍板、写成 spec；实现以 Claude Code 为主，Codex 可选。spec 不够用时停下说明缺什么，不自己补架构。
2. **升 heavy**：除受管区列出的安全、权限、沙箱、凭据等条件，碰 Tape、提示层的 spec 也升 heavy。
3. **逐条替换的范围**：只限表现层条款。`implemented` 的 spec 里，只涉及界面文案、布局或组件形态的条款，可以被后续 spec 逐条替换。「只涉及」的意思是：换掉之后，契约、Tape、IPC 通道与消息形状、权限语义和决策表全都不变；有一样要变，这条就不适用，仍走上面的 amend 或 supersede。一条条款里表现和契约搅在一起、拆不开的，也不适用。审批卡、拦截回执、授权弹窗上的按键与默认焦点、主次按钮、放行入口的有无与先后、确认步骤，以及任何会改变「按下某个键或按钮放行什么」的改动，都算权限语义，不适用本例外（例：02 里撤不回的卡「⏎ 一律是拒绝、默认焦点在拒绝、放行只能点「允许」或按 Space」）。「文案」只指界面上给人看的文字（locale 键的值）；写给模型的固定文本（提示层：系统提示、工具描述、`MODEL_NOTES` 等）不在此列，照 amend / supersede 与提示层的版本规则（02 §提示层与评测）走。写明一次批准放行什么、范围多大、管多久、有什么后果的文字算权限语义的一部分：替换后的文案仍须写明这几样，否则不适用。
