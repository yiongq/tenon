# Tenon 的规格驱动开发（SDD）

规格是主产物，代码服务于规格。对实质性的工作，先写一份 RFC 式的 `spec.md` 说清问题、行为、设计决定、不变量和验收标准，再动手。小改动不走这套。

这套做法参考了 DeepChat 的 `docs/spec-driven-dev.md`（Apache-2.0）并按 Tenon 的分工简化：**架构由 owner 拍板、写成 spec，在哪个会话里讨论都行；实现以 Claude Code 为主，Codex 可选**，`spec.md` 就是各方的交接物。

## 什么时候走 SDD

走：新模块、跨模块改动、数据迁移、公开契约（IPC / 桥协议 / 插件格式）、运行时架构、安全边界、以及任何"半年后有人会问为什么这么定"的决定。

不走：样式和文案、单一模块内的局部逻辑、常规文档修订、版本号与发版元数据。

判断标准只有一条：**如果一个能干的开发者拿到需求后必须自己发明架构，就需要 spec；如果他只需要在既有边界内写代码，就不需要。**

## 目录

每个目标一个 kebab-case 文件夹，按性质放：

- `docs/architecture/<goal>/` — 重构、迁移、依赖边界、共享契约、运行时架构、跨模块设计。**阶段性工作也在这里**，以两位数序号开头（`00-foundation`、`01-provider-and-tape`…）。
- `docs/features/<goal>/` — 新功能、用户可见能力、集成、工具。
- `docs/issues/<goal>/` — 复杂 bug、回归、可靠性问题。

每个文件夹两个文件：

- `spec.md` — RFC。只保留有实际信息的段落，从这些里选：背景与问题、目标与非目标、现状与方案、所有权与依赖方向、接口与数据流、不变量与失败行为、兼容与迁移、安全 / 隐私 / 性能约束、**验收标准**、开放问题、被否决的方案。
- `plan.md` — 有序的实现步骤和它们的完成状态，包括最终审查、验证决定、清理和质量门。**这是唯一的执行跟踪，不建 `tasks.md`。**

复杂 bug 通常只要 `spec.md`（问题、影响、根因、修法、简短清单、验证结果、关联 issue）。

## spec 怎么写

- 写到"能干的开发者不用发明架构就能做局部决定"的程度，不写到伪代码。
- 接口用 TypeScript 签名给出，字段名是真实的。
- 不变量单独列，每条一句话，能写成断言或测试。
- **验收标准描述可观察的结果或可独立验证的契约**，不描述实现。好：「应用重启后未回答的权限弹窗仍在且可回答」；坏：「权限状态持久化到 SQLite」。
- 开放问题写清"什么时候、依据什么能定"，而不是留白。
- 顶部一行 `Status:`——`draft` / `ready` / `implemented` / `superseded by <link>`。
- 顶部可选一行 `Revisions:`——记录同一份 spec 内的就地修订：日期 + 改了哪个字段 + 旧的是什么 + 为什么。`Status: implemented` 之后不再使用。
- 顶部可选一行 `Amends:` / `Amended by:`——后续 spec 对一份 `implemented` spec 做只增不改的修补时，两边各写一行互指，规则见「改变决定」。`Replaces:` / `Clauses replaced by:` 同理：后续 spec 逐条替换一份 `implemented` spec 里只涉及表现的条款时两边各写一行，规则见「改变决定」的第三个例外。

## plan 怎么维护

- 步骤有序，每步一行，前面 `[ ]` / `[x]`。
- 实现过程中发现的新步骤直接加进去，不另开文件。
- 最后三步固定：对照验收标准逐条验证、清理临时探针和测试、更新 spec 的 `Status`。
- plan 不复制 spec 的内容，只引用。

## 改变决定

不改旧 spec。新建一个 spec 说明改了什么、为什么、旧的哪些部分作废，旧 spec 顶部标 `Status: superseded by <link>`。决策记录只追加不改写，半年后仍能看到"当时为什么那么定、后来为什么推翻"。

例外：spec 还是 `draft` / `ready`、且尚无代码依赖该契约时，可以就地修订，条件是在顶部 `Revisions:` 写清日期、改了什么、旧的是什么、为什么改。一旦 `Status: implemented` 或已有代码依赖，除下面两个例外，只能新建 spec supersede。

第二个例外——**修补（amend）**（2026-09-17 owner 确认）：`implemented` 的 spec 可以被后续阶段的 spec 修补，条件是**只增不改**——新增接口成员、新增枚举值、收紧一个原本未限定的选型——且不推翻任何既有决定、不改变任何既有成员的形状。做法：被修补的 spec 在 `Status:` 之下加一行 `Amended by: <link>（日期：增了什么）`，`Status` 不变、正文一字不改；修补的全文、日期与理由写在做修补的那份 spec 里，它的顶部用 `Amends:` 指回去。凡是改动或移除既有内容，仍须 supersede。为加一个成员而作废整份旧 spec 不成比例，「部分 supersede」又会让旧 spec 一半有效却没有规则说是哪一半，所以单列这一条。第三个例外——**替换表现层条款**（2026-10-15 owner 确认）：`implemented` 的 spec 里，只涉及界面文案、布局或组件形态的条款，可以被后续 spec 逐条替换。「只涉及」的意思是：换掉之后，契约、Tape、IPC 通道与消息形状、权限语义和决策表全都不变；有一样要变，这条就不适用，仍走上面的 amend 或 supersede。一条条款里表现和契约搅在一起、拆不开的，也不适用。审批卡、拦截回执、授权弹窗上的按键与默认焦点、主次按钮、放行入口的有无与先后、确认步骤，以及任何会改变「按下某个键或按钮放行什么」的改动，都算权限语义，不适用本例外（例：02 里撤不回的卡「⏎ 一律是拒绝、默认焦点在拒绝、放行只能点「允许」或按 Space」）。「文案」只指界面上给人看的文字（locale 键的值）；写给模型的固定文本（提示层：系统提示、工具描述、`MODEL_NOTES` 等）不在此列，照 amend / supersede 与提示层的版本规则（02 §提示层与评测）走。写明一次批准放行什么、范围多大、管多久、有什么后果的文字算权限语义的一部分：替换后的文案仍须写明这几样，否则不适用。做法：做替换的 spec 在顶部用 `Replaces:` 写明被换的条款、日期和理由，新条款的全文写在自己里面；旧 spec 在被换的那一条所在行的行末接一句指针「（<日期> 起由 <link> §x 取代：一句话说换成了什么）」，不新起一行，旧文留着不删、不改一个字；旧 spec 顶部再加一行 `Clauses replaced by: <link>（日期：哪几条）`，`Status` 不变。为一个按钮的位置、一句提示的措辞去作废整份旧 spec 不成比例，而 amend 又管不了「改」，所以单列这一条。

跨阶段的技术选型另外写 ADR 放 `docs/adr/`，格式见 `adr-001`。

**公开与私有的边界**：仓库是公开的。影响贡献者和用户的决定（许可证、边界、接口、取舍）进公开的 spec / ADR；市场判断、定价、目标客户、营收、谈判相关的内容不进仓库，放仓库外的私有笔记，ADR 里只留一句「另记」。

## 和代码 agent 的交接

- 开工不需要指令。agent 自己找当前阶段：序号最小、`Status: ready`、`plan.md` 里还有未勾选步骤的那份 spec（没有这样的 architecture spec 时，找 `docs/features/*/spec.md` 里 `Status: ready` 且 plan 有未勾选步骤的那份，同时有两份就问），从第一个未勾选的步骤（或交接记录里写的半成品状态）接着做，动手前说一句选了哪份 spec 哪一步。要指定别的目标时才说「按 `docs/<...>/spec.md` 实现」。
- agent 读 `AGENTS.md`（硬规则）→ 读 spec → 维护 plan → 跑门禁 → 标 status。
- spec 不够用时 agent 应停下来说缺什么，而不是自己补架构。缺的部分由 owner 拍板后补进 spec。
- 门禁（format / lint / typecheck / test）由 git hooks（lefthook）和 CI 强制，对 Claude Code、Codex 和人一视同仁，不依赖 agent 自觉。
- **以 Claude Code 为主，Codex 可选**：用到 Codex 时由 Claude Code 派给它边界清楚的任务。各 agent 互不记得对方的会话，`plan.md` 是唯一的交接面。每次停下之前必须把"做完的 / 做到一半的（代码停在什么状态）/ 下一步"写进 `plan.md`；同一个 worktree 同一时间只让一个 agent 干活，并行用 `git worktree`。

## 主参考与 spec 的关系

`docs/architecture/master-reference.md` 是"从哪来"：所有决策、参考项目、取舍都在那里。各阶段的 `spec.md` 是"做什么"：从主参考里裁出当前阶段需要的部分，补上接口和验收标准。主参考不直接指导编码；spec 才是。主参考的 §13 是各阶段 spec 的目录。

## 批准与修订（2026-10-22 起）

- spec 改成 `ready`、改成 `implemented`，只由 owner 定。请 owner 回一句点名这份 spec 的话，比如「05 改 ready」，在 spec 页头记一行 `Approved: ready · <日期> · 「<owner 原话>」· <出处：对话，或 PR #n>`。
- 不算批准：去掉标点和空白后只是「继续」「开工」「好」「好的」「可以」「行」「ok」「都按推荐」「按推荐」「全部按推荐」；或者没点名这份 spec（两位编号、目录名或标题）。「继续」「开工」照旧用来开工（见「和代码 agent 的交接」），但从不改状态。整批采纳推荐项要写明范围，比如「05 D1–D12 按推荐」；选错难退的卡，每张另写一行，比如「D7=A」。
- `implemented` 之后不往回退。`ready` 退回 `draft`，只在 owner 说的时候，并记一行修订。
- 从 `ready` 起，spec 的每次改动在修订记录里记一行：日期 · 哪一节 · 为什么 · 相关的提交号或 `PR #n`。实现中只收紧或澄清的，可以直接改，和代码放在同一个 PR 里；放宽要求，或改已合入的接口，先要 owner 点名批准。
- 从 05 起按这些规矩；00–04 保留现有的记录。04 的 `implemented` 由 owner 在加这一节的 PR 里确认。
