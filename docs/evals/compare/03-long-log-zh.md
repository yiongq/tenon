## 差在哪

- **A 与 B**：都写对 E-6801；B 的回复指到对账服务单元测试的「按渠道汇总金额」用例（A 的回复原文记录里没留）。A 的命令输出落盘 1 次（84 932 字节），模型没有对落盘文件调 Read 或 Grep 工具，另跑了 1 条命令（共 2 张命令卡），那条命令的原文没留存。B 的录屏只有 4 个工具的步骤标签，长输出怎样交给模型（截断、落盘还是分段）看不到。
- **C 与 D**：都写对，轮数相同。C 的输出同样落盘 84 932 字节，模型对落盘文件用了 2 次 Grep 工具，读本会话的落盘文件不出卡。D 这边 Claude Code 只把约 1 万字的开头交给模型（全量约 4.55 万字，错误行在约 3.7 万字处，模型没看到），没有落盘文件；模型自己改成 `node nightly.mjs > /tmp/nightly.log` 再 grep，在工作区外写了文件，命令卡 3 张，其中 /tmp 重定向和对 /tmp 的 grep 各 1 张。D 首次尝试因驱动规则错误作废，这条是重跑。

## 原因

- 长输出处理（H9）：Tenon 超过落盘阈值时把全文写进本会话的落盘目录，给模型预览和路径，模型可以用 Read 分段读或 Grep 查；Claude Code 把输出截到约 1 万字，模型只能自己重定向到文件再查，这多出了命令卡，也让它写到了工作区外。Cowork 怎样处理长输出，本次证据看不到。
- 卡数差异另见 [已知差异 #1](../README.md#已知差异清单)：Tenon 每条不同的命令原文各问一次，Cowork 在已连接的文件夹里没有逐次卡。
- 费用：C 与 D 同入口同单价，D 的 transcript 用量是未命中缓存的输入 13 805、缓存读 112 128、输出 847，C 是 28 107、21 120、960。
