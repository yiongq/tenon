## 2026-11-28 · owner 定的

### D1 · 这份 spec 按哪一档写
- A ★ heavy：先实测再写。四路调研、每路一份对抗核实，探针在批 ready 前跑。代价：起草更慢，探针要占 CI 时间。
- B standard：直接按调研写。代价：Electron 与打包后的行为（转储、主进程异常、helper 路径、钥匙串、签名）没实测，写错了要到实现或出包时才发现。

选错难退吗：不难。只影响把关多严。
结果：A · 2026-11-28（问卷）。

### D4 · 「给你看的一页」用不用新格式
- A ★ 当试点：只在这份 spec 里手工用新格式（一张图、一个带数的例子、「你做 X → 你看到 Y」的场景、你定过的事逐条写），sdd 模板和 spec-check 不改。代价：这一页和别的 spec 长得不一样，仍要过现有检查。
- B 照旧格式。代价：新格式好不好用没有实例可看。

选错难退吗：不难。只是一页的写法。
结果：A · 2026-11-28（问卷）。

### D5 · 留不留崩溃转储
- A ★ 不留：不启动 Electron 的崩溃收集，只记结构化的退出记录。代价：底层原生崩溃没有现场，只知道哪个进程、什么原因。
- B 本机留，最多 3 份：启动崩溃收集、不上传，启动时删多的。代价：转储可能带进程内存片段，按 Crashpad 的设计文档一般还带命令行和环境，含密钥也没法脱敏，要给「机密不进日志」开例外（E3）。

选错难退吗：不难。以后要转储只加一处启动调用；B 退回 A 要清掉已落盘的转储。
结果：A · 2026-11-28（问卷）。

### D8 · 界面里的报错记不记进日志
背景：界面（渲染进程）里的报错今天只进开发者工具的控制台，安装版的菜单里没有开发者工具，所以完全看不到（E1）。lead 转述的范围里有一句「把只打到控制台的报错写进日志」，界面的控制台也是其中一处。
- A 不记：只记界面向后台的请求失败和渲染进程崩溃。代价：白屏、界面里没接住的异常在日志里一行都没有。
- B ★ 只记错误级的第一行：主进程从 Electron 已有的控制台消息事件里取级别为错误的，只留第一行、截到 300 字、脱敏，加来源文件名和行号；不加新的 IPC 通道。代价：报错文字偶尔带页面上的内容片段；同一个错误反复出现会刷屏，靠轮转兜底。
- C 加一条新通道，界面把完整的错误栈发给主进程。代价：要在 contracts 里加通道、限频、防界面刷日志；栈里带的内容更多。

最小方案为什么不行：界面白屏和界面里没接住的异常是最常遇到、又最说不清的问题，A 下日志对它们没用。
选错难退吗：不难。B 退到 A 删一个监听；B 改 C 要加通道。
结果：B · 2026-11-28（问卷）。owner 选 B 时看到的代价就是上面这一段。之后评审指出渲染进程按「可能被攻破」看待、能故意刷屏，后来加了限量，见 D20。

### D13 · 日志和安装包拆不拆成两份 spec
- A ★ 拆成两份：错误日志先做；安装包等日志做完、探针跑完再批。代价：两份各自维护；安装包的冒烟要读日志，依赖错误日志那份先做完。
- B 一份做到底。代价：安装包的细节大多要等探针，整份都批不了 ready，日志这一半本来可以先动手。

选错难退吗：不难。还没开工，合回去只是搬文字。
结果：A · 2026-11-28（问卷）。

## 2026-11-28 · 评审与复审之后 owner 定的

### D15 · 启动失败提示框与「打开日志文件夹」做不做
背景：这两项都不是日志本身，原先的文件里指不回 owner 的原话（挑刺评审指出，另记）。
- A ★ 两项都做：启动失败时弹框写明日志在哪；帮助菜单里加「打开日志文件夹」。代价：多两处界面文案与接线；打包构建的菜单从此有「帮助」，要改两条现有测试。
- B 只做启动失败提示框。代价：要找日志得自己去数据目录里翻。
- C 两项都不做。代价：安装版启动失败时一闪就没，用户不知道去哪找日志。

最小方案为什么不行：日志写进了一个用户不知道的文件夹，等于没写；启动失败正是最需要它的时候。
选错难退吗：不难。去掉一个菜单项或一个弹框。
结果：A · 2026-11-28（问卷）。

### D16 · 机密怎么不进日志
- A ★ 三层，读到密钥时就登记：① 错误只记固定字段；② 主进程每次从钥匙串或环境变量读到密钥、拼出令牌时当场登记，日志里出现就替换；③ 正则兜底。先脱敏再截断。代价：登记点要列全（§日志怎么写「脱敏」），漏一处就只剩正则；OAuth 令牌在 kernel 里拼出，要多一条交给 desktop 的路（D19）。
- B 两层，不登记：只靠固定字段与正则。代价：格式不常见的 key（智谱、DeepSeek、不透明的 OAuth 令牌）正则认不出，会原样落盘（E5、E8）。

选错难退吗：不难。登记表只在内存里，不落盘。
结果：A · 2026-11-28（问卷）。

### D17 · 日志放哪、写成什么格式
- A ★ Tenon 数据目录里已有的日志文件夹（`<profileDir>/logs/`），一行一条 JSON。代价：profile 打开之前的失败要先存在内存里；格式定了以后要改就得升格式版本。
- B 系统日志目录（macOS `~/Library/Logs/…`）。代价：不在沙箱与文件工具的保护名单里，agent 读得到；路径里没有 tenantId。
- C 同目录、纯文本。代价：测试容易测空；值里的换行能伪造出一行假的日志。

选错难退吗：中等。安装包那份的冒烟要解析这个格式；运行标记会被下一次启动读回来。
结果：A · 2026-11-28（问卷）。

### D18 · 连接器（MCP）的日志要不要一起管
背景：MCP server 的 stderr 写在同一个日志文件夹里，每台 3 份、每份 1 MB，台数不限；权限是 0644；只换已知的 `env_keys` 与头的值（03 §进程树、stderr 与日志；E8）。
- A ★ 只改权限：给 03 加一条增补，MCP 日志也改成只有本人能读（0600）；数量上限和脱敏不做，记进「以后再说」。代价：文件夹里仍有不受上限、只按已知值脱敏的文件，「打开日志文件夹」时一并给人看到。
- B 权限、上限、脱敏一起改。代价：改 03 已实现的更多行为，范围变大。
- C 不管。代价：同一个文件夹里有别的用户读得到的文件。

选错难退吗：不难。
结果：A · 2026-11-28（问卷）。卡面写明了这一项要给 03 加一条增补（§对 03 的增补 第二条）；owner 的原话没有单独点 03，对 03 的改动随「error-logs 改 ready」一并批准。

### D19 · kernel 拼出的 OAuth 令牌怎么交给日志去登记
背景：D16 要求「拼出令牌时当场登记」。MCP 的 OAuth 令牌在钥匙串里是分片存的（base64url 的 JSON 切成几片），client secret 在整段 JSON 里，拼出整段的是 kernel（`packages/kernel/src/mcp/token-store.ts`、`oauth.ts`），desktop 包住 `host.secrets` 只看得到片与 JSON（E8）。要拿到裸值，就得改 03 已合入的接口，所以出卡。
- A ★ 03 §接口 的 `McpPoolOptions` 只增可选成员 `onSecret`：连接池每往某台 server 的脱敏表里加一个值，同时交出来；desktop 接到登记表。代价：给 03 写一条只增可选成员的增补，03 页头加一行回链。
- B desktop 自己照 kernel 的存储格式解片。代价：desktop 和 kernel 的存储格式绑死，kernel 改格式时 desktop 悄悄失效。
- C 不登记 OAuth 令牌，只靠正则。代价：不透明令牌出现在报错正文或 JSON 片段里就原样落盘（安全视角评审的小程序实测，另记）。

选错难退吗：不难。可选成员，不传时行为不变。
结果：A · 2026-11-28（问卷）。这也是 owner 对「给 03 §接口 加 onSecret」的点名同意。

### D20 · 两道保护：按来源限量、打开日志前检查文件
背景：复审指出这两样都是新机制、碰安全，限量还改了 D8 选 B 时的代价，该出卡（另记）。
- A ★ 两条都要：① 每个来源每分钟最多 60 行，超了只记一句「此来源已限量、丢了 N 行」；② 打开日志文件前检查不是链接、属于本人，不对就拒绝写。代价：刷屏那一分钟的大部分行会丢；检查不过时这次启动不写日志，只往 stderr 报一句。
- B 只要限量。代价：日志文件被换成链接或硬链接时，日志行会被写进别的文件（评审的小程序把一行日志写进了 shell 配置文件）。
- C 只要文件检查。代价：界面或沙箱里的一条命令几百毫秒就能把前面的证据挤出日志（评审小程序实测）。
- D 都不要。代价：上面两样都有。

最小方案为什么不行：两个不可信的写入方（界面、Linux 沙箱观测器）都能往日志里写，日志文件夹又可能被预先放了链接；只做一道，另一样的证据都在评审里跑出来了。
选错难退吗：不难。去掉一个上限或一段检查。
结果：A · 2026-11-28（问卷）。

owner 选定之后补充的实现细节（属自定范围，各在「agent 自定」里记一行，不推翻就算认可）：主进程没接住的错（`main.uncaught`）单独每分钟 600 行；九种行不限量（启动、上次没正常退出、启动失败、退出、窗口出来了、沙箱状态、沙箱 helper 路径、进程退出、限量的计数那一行）；每次轮转后把本次启动的五种生命周期行抄进新文件开头；界面报错的来源文件名截到 200 字。来源怎么算、检查到哪一步，写在 spec §日志怎么写「限量」与 §一直要成立的规矩。

## 2026-11-28 · 段一复审之后 owner 定的

### D21 · 登记的密钥数量设不设上限（段一复审后补问）

- A ★ 上限 1 万，丢最久没用的：常用的 key 每次读到都排到最前。代价：被灌满后，很久没用的密钥只靠格式识别兜底。

- B 继续写进旧文件。代价：大小上限失效，违反验收 13。

- B 不换，写进已知限制。代价：日志里可能留下密钥的前 8 到几十个字符。

## agent 自定

原先的「脱敏分三层」「日志放哪」「日志行的格式」三行，评审后改由 D16、D17 定；「按来源限量」「文件保护」两行，复审后改由 D20 定，这里不再记。D20 选定之后补的细节，下面各记一行。

起草者（lead）事先定的四项：
- 自定：放哪 · `docs/features/error-logs/`，不占 architecture 编号，不进阶段表 · 和 auto-tier-hardening 这类 features spec 一样；07 已留给扩展层
- 自定：日志库 · 自写小写入器，不引入第三方日志库 · 写入口只收带类型的事件才守得住脱敏；electron-log 的渲染通道与「IPC 只走 contracts」冲突；DeepChat 有同样的先例（E6）
- 自定：日志里不写什么 · 路径里的主目录换成 `~`；不记模型对话内容，不记完整命令行、环境变量与错误对象的 `cmd`、`spawnargs`、`env` · 主目录只为藏用户名，项目名与文件名照记（写进已知限制）；对话与命令行可能带机密（E5）
- 自定：菜单位置与文案 · 「打开日志文件夹」放在「帮助」菜单，开发构建与打包构建都有；提示框与菜单文案走 i18n（zh-CN 与 en） · VS Code、Mattermost 都放在帮助或开发者菜单类里（E6）；做不做由 D15 定，位置是起草者选的

起草中定的：
- 自定：时间写法 · 本地时间带时区偏移，ISO 8601 到毫秒 · 对得上自己的钟，又不含糊
- 自定：上限 · 单个文件 5 MiB，加上下一行会超过就先轮转；留 2 份旧的，合计不超过 15 MiB；单行 16 KiB；字符串字段 2000 字 · 同类做法在 1–10 MiB、留 1–3 份之间（E6）
- 自定：怎么写盘 · 同步写一个一直开着的文件，追加模式；启动时给上次的半行补换行 · 同步写返回时数据已交给内核，进程崩了也留得住（E6）
- 自定：开日志之前的行 · 先存在内存里，最多 200 行，开了再写进去，溢出的记一行 · 单实例锁之后、profile 打开之前也会有报错
- 自定：先脱敏再截断 · 每个字符串字段先脱敏、再截断，整行最后再过一遍；登记值按长度从长到短替换 · 先截断会留下半截机密，先换短的会留下长的那个的尾巴（E8）
- 自定：通用格式的范围 · 在 `sk-`、`Bearer`、JWT、网址参数、`Authorization:`、PEM、`user:pass@` 之外，补上 `gh[opusr]_` 等常见前缀与网址参数名，参数名不分大小写（§日志怎么写「脱敏」第 3 层） · 不在登记表里的值（工具的报错、MCP 网址的查询串）只能靠格式；GitHub 的 OAuth 令牌是 `gho_`、`ghr_` 开头
- 自定：漏登记由什么守 · 主进程只有一个 `HostSecrets`，在 `host/index.ts` 里包上 `rememberingSecrets`，静态测试守住别处不 new；每个登记点一条走真实路径的哨兵用例 · 新加一处读机密的代码，只要还经 `host.secrets` 就自动登记
- 自定：级别的含义 · error 是出了错要看，warn 是降级、被拒或被丢，info 是生命周期与提示；各转发器照这个定级，「N 个会话可续跑」记 info · 原来照 console 方法定级，正常启动也会出错误级的行
- 自定：主进程没接住的错 · 异常只用 `uncaughtExceptionMonitor` 记；单独的 Promise 拒绝用一个只记一行的 `unhandledRejection` 监听；不注册 `uncaughtException` · P2 实测：注册 `uncaughtException` 会关掉 Electron 自己的弹框；拒绝到不了 monitor，加了 `unhandledRejection` 也照旧不弹框、不退出（E4）
- 自定：怎么知道上次没正常退出 · 启动时在日志文件夹写运行标记，正常退出时删，启动时还在就由 `open` 自己记一行（读不出也记） · 被强杀、断电时 JS 来不及跑，只有残留标记能说明（E4）
- 自定：SIGTERM 怎么写 · 照实写三种情形：srt 装上信号监听之前是正常退出，装上之后、Tenon 登记之前只让 srt 复位、不退出，登记之后是正常退出；不为此另加信号监听 · 复审更正了上一稿写反的事实（04 §退出、`e2e/stop-exit.spec.ts` 的注释）；安装包那份的冒烟等沙箱状态那一行出来再发 SIGTERM（E7）
- 自定：接口不依赖 Electron · `appLog` 不 import electron，版本与路径在 `open` 时传入；「记一行 → 等 ready → 弹框 → 退出」与「打不开时弹框」抽成 `reportStartupFailure`、`openLogsFolder` · chat.ts、host/profile.ts 这类模块刻意不碰 Electron，单元测试在 Node 里跑；index.ts 末尾的 catch 测不到（E7）
