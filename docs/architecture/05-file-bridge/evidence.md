## 探针

三台机器：macOS（arm64，git 2.50.1，Apple 命令行工具里的 git；`diskutil` 在沙箱里跑不起来，文件系统只有 statfs 类型号 26，按 APFS 理解）；Ubuntu 24.04 与 26.04 两台 Lima 虚拟机（arm64，git 2.43.0 / 2.53.0；`stat -f -c %T` 报 `ext2/ext3`，即 statfs 魔数 0xEF53，分不出 ext4）。Node 都是 22.22.0。耗时是同一进程串行三轮的中位数，合成负载：1 万或 5 万个 1–8 KiB 文本加 32 个 1 MiB 二进制，另有被 `.gitignore` 排除的 2 万个小文件。macOS 先在另一个 agent 的沙箱里跑了全部十项，2026-10-23 又在沙箱外重跑了快照与还原两项；macOS 的耗时以沙箱外那组为准，沙箱里那组只作旁证（慢约三成），行为类结论两组一致。

### P1 · 整树快照要多久

- 目的：定「每次会改动的调用之前整树拍一张」是否可行，以及首张与之后各张的预算。
- 结果是 X 就改什么：之后各张在 5 万文件上超过 1 秒，就改成只给文件工具拍（主参考 §13 阶段 4 的砍法第二步）；首张超过几分钟，就改成后台拍并设上限。
- 实际结果（5 万文件，默认配置 / 调优配置，毫秒）：

| 平台 | 首张 | 无改动 | 改 1 个 | 改 1% | 新增 100 |
|---|---:|---:|---:|---:|---:|
| Ubuntu 24.04 | 6174 / 6208 | 70 / 69 | 77 / 63 | 874 / 835 | 124 / 122 |
| Ubuntu 26.04 | 8759 / 9004 | 117 / 71 | 111 / 65 | 1011 / 1090 | 91 / 108 |
| macOS（沙箱外） | 33872 / 34003 | 128 / 142 | 132 / 133 | 1019 / 1022 | 153 / 127 |
| macOS（沙箱里，旁证） | 45987 / 50530 | 232 / 174 | 195 / 162 | 1552 / 1281 | 248 / 185 |

  5 万文件另加一次遍历、读纳秒 mtime：探针写死裁掉 `node_modules` 后 Linux 170–255 毫秒、macOS 约 250 毫秒，不裁 Linux 316–559 毫秒、macOS 379–534 毫秒；探针的裁法不是完整的 gitignore 解析，真实现按影子仓库的忽略规则列文件的耗时没测（P17）。1 万文件：首张 Linux 1.6–2.2 秒、macOS 6.2–7.7 秒；之后各张 Linux 约 20 毫秒、macOS 约 50 毫秒；裁掉 `node_modules` 后遍历 32–56 毫秒。
- 结论：事先定的判据被触发了一列。无改动、改 1 个、新增 100 三列在三台机器上都远低于 1 秒；「改 1%」一列（500 个文件，含全部 32 个 1 MiB 二进制）在 macOS 沙箱外与 Ubuntu 26.04 上略超 1 秒（1011–1090 毫秒）。不砍，理由：一次调用改 500 个、含 32 MiB 二进制不是典型情形；之后每张有 D5 的 5 秒预算兜底，超了这个会话自动改为只留单文件副本，砍法第二步的效果在超预算时就会自动出现。首张按 D5 后台拍，预算照 D5 已定的数字，不据这些数字改。默认与调优两组配置互有快慢，没有一致的赢家（D36）。
- 平台：macOS、Linux 已测。

### P2 · 影子仓库能不能不受用户 git 配置影响

- 目的：用户的全局 `excludesFile`、钩子、`fsmonitor` 会不会让快照漏文件或执行用户的代码。
- 结果是 X 就改什么：隔离后仍有钩子运行，就不用本机 git（改选纯 JS 实现，回到 D4 重选）。
- 实际结果：用假的主目录放一份「用户全局配置」作正对照，未隔离时被排除、钩子运行；隔离后（环境只留 `PATH`，`HOME` 指影子目录，`GIT_CONFIG_NOSYSTEM=1`，`GIT_CONFIG_GLOBAL` 指空文件，`core.hooksPath` 指空目录，`core.fsmonitor=false`，`core.excludesFile`、`core.attributesFile` 指空文件，空模板 `init`）被排除的文件照样进快照、钩子没运行。三台机器结果相同。文件属主不同的工作区（`safe.directory`）没测。
- 平台：macOS、Linux 已测。

### P3 · `.git` 与嵌套仓库

- 目的：工作区自己的 `.git`、工作区本身是 git worktree、子目录里的嵌套仓库与 submodule，进不进快照。
- 结果是 X 就改什么：只排除 `.git` 就够，规则写一行；不够，就要按嵌套根整根排除。
- 实际结果：根下 `.git` 是目录或指针文件时都不进影子索引。嵌套仓库与 submodule 默认被记成 gitlink（`160000`），只排除 `.git` 不够；对嵌套根再写一行 `/sub/` 才整根排除。排除要写在拍首张之前：已进索引的路径，后加的 `info/exclude` 挡不住。三台机器结果相同。
- 平台：macOS、Linux 已测。

### P4 · 符号链接与大小写

- 目的：链接进快照存的是什么、还原回来是什么；大小写不敏感的卷上改名后还原的结果。
- 结果是 X 就改什么：链接被跟随读进目标内容，就要在拍之前单独处理链接。
- 实际结果：指向工作区内、工作区外和悬空的三种链接都按链接文本存（`120000`），还原后仍是链接、文本不变，不读目标。macOS（大小写不敏感）上 `A.txt` 改名成 `a.txt` 再还原，目录项回到 `A.txt`；Linux（区分大小写）上改名等于删一个、新建一个，探针这一步的还原不删新文件，所以还原后两个名字都在；Tenon 的还原把 `a.txt` 当这一轮新建的删掉（D16）。
- 平台：macOS、Linux 已测。

### P5 · 按快照还原要多久、还原得对不对

- 目的：定还原用整树检出还是只动改过的路径，以及还原后的内容与 mtime。
- 结果是 X 就改什么：整树检出在 5 万文件上超过几秒，就只动改过的路径。
- 实际结果：改前 1%、删 10 个、新建 50 个之后还原，两种 git 做法内容全部一致、新建的都能列出并删掉、被排除的 2 万个文件没被碰。git 写回的文件 mtime 变成当前时间（第一版据此要另记、另写回 mtime；D45 定了还原写当前时间之后不再需要）；整树检出会改写全部受管文件的 mtime。5 万文件上整树做法 Linux 3.4–3.9 秒、macOS 14.2–14.3 秒（沙箱外；沙箱里 15.7–17.3 秒）；1 万文件 macOS 2.2–3.0 秒。这些只作还原耗时的上限参考：还原只动改过的路径（D24），动得越少越快。macOS 沙箱外这组还原后内容同样全部一致，mtime 写回最大误差 1229 纳秒。
- 平台：macOS、Linux 已测。

### P6 · mtime 写回的精度

- 目的：定「还原后 mtime 回到任务前」怎么比。
- 结果是 X 就改什么：写回误差超过 1 微秒，验收就不能按微秒取整相等比，要改成带容差。
- 实际结果：`utimes` 传以秒为单位的浮点数时，1000 次里误差在 −1212 到 +167 纳秒之间，有 82 次按微秒取整后不等；传 `Date` 误差到 −137 微秒（只到毫秒）。真实还原里写回全部受管文件的最大误差 1202–1230 纳秒。三台机器结果相同（误差来自浮点换算）。据此「按微秒比」曾定义成两个 mtime 之差的绝对值小于 2 微秒，不用 `Date`（D25）。owner 2026-10-23 定还原写成还原那一刻的时间（D45）之后，这条不再用于验收，只留作背景。
- 平台：macOS、Linux 已测。

### P7 · 硬链接

- 目的：Tenon 的 Write 会不会写穿硬链接。
- 结果是 X 就改什么：写穿，就照 D10 在写入边界查名字数。
- 实际结果：两个名字时 `nlink` 读出 2；原地截断再写，两个名字一起变；写临时文件再改名会拆成两个各 1 个名字的文件。Tenon 的 Write、Edit 现在是原地写（`apps/desktop/src/main/host/fs.ts` 的 `DesktopFs.writeFile`），会写穿。三台机器结果相同。
- 平台：macOS、Linux 已测。

### P8 · 机器上有没有可用的 git

- 目的：D4 用本机 git 时，怎么判断有没有、会不会弹安装框。
- 结果是 X 就改什么：没装开发者工具的 Mac 上调用 `/usr/bin/git` 会弹框，就先用 `xcode-select -p` 探测、失败就不碰它（D4 已这样定）。
- 实际结果：macOS 上 `/usr/bin/git` 是开发者工具的转发程序（链接 `libxcselect`，`xcrun --find git` 指向命令行工具里的实体）；本机装着命令行工具，所以没装时的行为未验证。两台 Ubuntu 上 `/usr/bin/git` 是普通可执行文件。
- 平台：macOS 部分已测（没装命令行工具的情形未验证）；Linux 已测。

### P10 · 单个文件超过上限怎么挡

- 目的：git 没有「跳过大于 N 的文件」的选项，比较先排除与后移出两种做法。
- 结果是 X 就改什么：后移出明显更快且不留大对象，就用后移出；否则先排除。
- 实际结果：5 万文件加 5 个 200 MiB 稀疏文件，先遍历找出大文件写进排除表再拍：Linux 6.8–7.6 秒、macOS 45.6 秒（沙箱里测，沙箱外没重跑这一项）；先拍再从索引移出：Linux 9.0–12.8 秒、macOS 38.4 秒（同上）。后移出会先把大文件内容写进对象库、移出后对象仍留着。据此先排除（D6、D19）。「原来进过、后来变大」的转换没测，spec 写成每张之前按遍历结果从影子索引移出。
- 平台：macOS、Linux 已测。

### P11 · 项目的 `.gitattributes` 会不会改字节

- 目的：项目里的 `text`、`eol`、`ident`、`filter`、`working-tree-encoding` 会让 git 存进去和写出来的字节与原文件不同；探针没覆盖。
- 结果是 X 就改什么：在影子仓库的 `info/attributes` 写 `* -text -ident -filter -working-tree-encoding` 后，带这些属性的文件还原前后字节一致，就照此写进 spec（现稿已这样写）；不一致，就改成这类文件按单文件副本处理。
- 实际结果（2026-10-24）：19 个文件，覆盖 `text`、`eol=crlf`、`eol=lf`、`ident`、`filter` 与无关属性，各带 LF、CRLF、混合换行，另有带 BOM 的 UTF-16 文件。影子仓库的 `info/attributes` 写了那一行之后，拍快照、改写、强制还原，19/19 个文件还原前后字节一致；故意放一份带 clean/smudge 的假全局配置也一样。不写那一行时，macOS 13/19、Linux 12/19 个文件还原后字节变了。走「一致」那一支，spec 照现稿写（D35）。
- 平台：macOS（git 2.50.1）、Ubuntu 24.04（git 2.43.0）、Ubuntu 26.04（git 2.53.0）已测。

## 挑刺评审 r1 的复现程序

下面 P12–P16 来自 2026-10-23 挑刺评审 r1 的复现程序（脚本另记）。它们照第一版草稿的字面搭一个隔离的影子仓库、做一次「只按起点与收尾的差写回、删新建的」还原，用来暴露草稿没规定的地方，不代表实现一定这么写。评审在 macOS 与 Linux 上跑过；起草人同日在 macOS（agent 沙箱里，m1 的 Seatbelt 一步因嵌套沙箱跳过，命令直接跑）重跑，结果一致。

### P12 · 还原会不会经父目录的链接写到工作区外；删与放的先后

- 目的：一轮里获批的命令把工作区里一个目录换成指向外面的链接；大小写不敏感的卷上把 `A.txt` 改名成 `a.txt` 并改了内容。照字面还原会怎样。
- 结果是 X 就改什么：写到了外面、或文件被弄没，就在 spec 里写死先删后放、逐路径查父目录的真实路径、叶子不跟随、新建排他、改名配对（D49），并各加一条验收。
- 实际结果：差异是 `A sub`、`D sub/a.txt`，照字面还原后工作区外出现 `a.txt`；同一轮先删新建、再放回，则留在工作区里。大小写一例：影子仓库 `core.ignorecase=false` 时差异是 `M A.txt`、`A a.txt`，先放回再删之后工作区为空。spec 已改（§一键还原、规矩 8、验收 39、40）。
- 平台：macOS、Linux（评审）；macOS（起草人重跑）。大小写一例只在大小写不敏感的卷上成立。

### P13 · 一轮里排除集合变了，还原会怎样

- 目的：命令在子目录放一个 `.git` 文件、清空 `.gitignore`、删掉嵌套仓库的 `.git`，路径在起点与收尾之间被排除或不再被排除。
- 结果是 X 就改什么：轮前就有的文件被删、或你之后的改动不问就被盖，就让每张快照记下自己收了哪些路径，三张都收了才动（D50），并加验收。
- 实际结果：被排除的一例差异 `D src/a.ts`、冲突为空，还原后你写的 v3 变回 v1；不再被排除的两例差异 `A .env.local`、`A vendor/lib/x.c`，还原把轮前就有的这两个文件删了。spec 已改（规矩 7、验收 41）。
- 平台：macOS、Linux（评审）；macOS（起草人重跑）。

## Codex 交叉评审的复现

P27–P29 对应 2026-10-24 另一个模型做的交叉评审（报告另记）。P27 是起草人写的小程序（另记）；P28、P29 是评审在内存宿主与现有代码上复现的，起草人读过报告、没有重跑。

### P27 · 同一路径被两次调用改过，中间你也改过
